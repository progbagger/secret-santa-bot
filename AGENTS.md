# AGENTS.md

Инструкции в этом файле действуют для всего репозитория.

## Контекст проекта

`secret-santa-bot` — асинхронный Telegram-бот для проведения «Тайного Санты» преимущественно в групповых чатах. Публичная часть сценариев проходит в группе, а назначения, пожелания и другие персональные действия — в личном чате с ботом.

Проект использует Python 3.14, aiogram 3, PostgreSQL через SQLAlchemy/asyncpg и Redis. Зависимостями и командами управляет `uv`.

Целевая структура приложения:

- `src/secret_santa_bot/bot/` — Telegram handlers, middleware, callback data и клавиатуры;
- `src/secret_santa_bot/services/` — бизнес-логика и оркестрация сценариев;
- `src/secret_santa_bot/repositories/` — доступ к PostgreSQL, Redis и внешним API;
- `src/secret_santa_bot/entities/` и `repositories/**/entities/` — модели данных;
- `alembic/` — миграции PostgreSQL;
- `tests/functional/` — функциональные тесты с реальными PostgreSQL/Redis и fake Telegram API;
- `tests/units/` — изолированные тесты простой детерминированной логики.

Если нужного каталога ещё нет, создавай его только вместе с первой относящейся к нему функциональностью. Не добавляй пустые архитектурные слои заранее.

## Общие правила изменений

- Делай минимальные изменения, решающие задачу в корне, и сохраняй существующую архитектуру.
- Не смешивай рефакторинг, не относящийся к задаче, с фичей или исправлением.
- Поддерживай Python 3.14 и асинхронный стиль проекта. Не добавляй синхронный I/O в async-пути.
- Добавляй точные аннотации типов. Для абстракций коллекций и callable предпочитай `collections.abc`; используй современные типы и синтаксис Python.
- Для структур данных предпочитай `dataclass`; используй `slots=True`, а для неизменяемых value objects — также `frozen=True`, если это соответствует модели.
- Пользовательские тексты бота и `README.md` ведутся на русском языке.
- Не добавляй секреты и реальные токены. Локальные `.env` должны оставаться вне Git.
- Для ожидаемых сбоев делай ошибки и логи диагностичными. Не подавляй `asyncio.CancelledError`: освободи ресурс при необходимости и пробрось отмену дальше.

## Приватность и правила игры

- Не показывай в групповом чате назначения участников, их пожелания, приватные сообщения и другие данные, предназначенные конкретному пользователю.
- Не записывай в логи пары жеребьёвки, тексты пожеланий и анонимных сообщений, токены, полные Telegram updates или другие чувствительные данные. Для диагностики используй идентификаторы сущностей и безопасные статусы.
- Используй числовой Telegram user ID как внешнюю идентичность пользователя. Username, имя и другие изменяемые поля профиля не должны участвовать в авторизации или уникальности.
- Учитывай, что бот не может первым начать личный диалог. Сценарий вступления должен явно привести пользователя в private-чат по deep link и проверить готовность личного канала до действий, требующих персональной доставки.
- Публичные сообщения показывают только безопасное состояние игры: организатора, сроки, число или список участников и текущий этап без секретных связей.
- Переходы между состояниями игры выполняй явно в сервисном слое. Нельзя регистрировать участников после закрытия регистрации или незаметно менять уже раскрытую жеребьёвку.
- Перед жеребьёвкой проверь все ограничения и существование полного допустимого назначения. Невозможная конфигурация не должна частично менять игру.
- Сохраняй всю жеребьёвку атомарно: каждому участнику назначается ровно один получатель, каждый участник становится ровно одним получателем, назначения самому себе и запрещённые пары отсутствуют.
- Источник случайности передавай в алгоритм через явную зависимость. В production используй подходящий криптографически стойкий источник, а в тестах — детерминированный.
- Повторная жеребьёвка после раскрытия должна быть отдельным явным бизнес-сценарием с понятными последствиями для участников, а не побочным эффектом повторной команды или retry.
- Анонимное сообщение создавай заново от имени бота. Не пересылай исходное Telegram-сообщение, если forward metadata может раскрыть отправителя.

## Архитектура и работа с данными

- Telegram-слой должен оставаться тонким: разобрать update, проверить доступ, вызвать сервис и сформировать ответ.
- Бизнес-правила и orchestration размещай в `services/`, а не в handlers или репозиториях.
- Репозитории отвечают за операции с конкретным хранилищем и преобразование строк или ответов во внутренние модели. Не переноси в них бизнес-сценарии ради сокращения service-функции.
- Предпочитай небольшие атомарные репозиторные функции. Объединяй сложную логику в один SQL-запрос только когда это необходимо для атомарности, конкурентной корректности, блокировки или заметной эффективности.
- Границы транзакций задавай в слое бизнес-логики (`services/`) вокруг полного изменения бизнес-состояния через `async with transaction():`.
- Репозиторные функции не должны самостоятельно делать `commit`/`rollback` или скрыто определять границы составного бизнес-сценария.
- Не удерживай транзакцию PostgreSQL во время запросов к Telegram, Redis или другого медленного сетевого I/O. Сетевой вызов и короткие транзакционные изменения состояния разделяй.
- Для конкурентных сценариев используй транзакции и row locks в PostgreSQL, атомарные reserve/update-запросы и Redis lease/dedupe с проверкой token/value.
- PostgreSQL является источником истины для пользователей, игр, участников, правил и результатов жеребьёвки. Не переноси долговременное состояние игры в Redis.
- Делай повторную обработку одного Telegram update или callback безопасной. Повторная доставка не должна второй раз регистрировать участника, проводить жеребьёвку или отправлять логически новое уведомление.
- При изменении схемы добавляй новую Alembic-миграцию. Не переписывай уже применявшиеся миграции без явной необходимости и обязательно проверяй upgrade на реальной PostgreSQL.

## Тестирование

### Выбор уровня теста

- По умолчанию предпочитай функциональный тест, проверяющий пользовательский или бизнес-сценарий через реальные границы приложения.
- Пиши unit-тесты для простой и детерминированной логики: parsing, formatting, validation, переходов состояний и алгоритма построения или проверки жеребьёвки.
- Если unit-тест требует большого количества моков или повторяет внутреннюю реализацию, подними его на функциональный уровень.
- В функциональных тестах используй настоящее приложение отдельным процессом, PostgreSQL и Redis из Docker Compose и fake-сервисы внешних протоколов. Предпочитай fake Telegram API мокам handlers, services или repositories.
- В функциональных проверках, fixtures и support не используй monkeypatch и не импортируй код приложения из `src`. Взаимодействуй с приложением через внешний протокол, а сохранённое состояние проверяй через SQL или специальные наблюдаемые endpoints fake-сервисов.
- Допустим отдельный тонкий bootstrap runner: он импортирует точку входа только для запуска приложения и передаёт управляемые зависимости. Бизнес-логика и прямые вызовы сервисов или репозиториев в runner недопустимы.
- Для времени и случайности используй внедряемые часы и генератор. Для ожидания фоновой работы проверяй наблюдаемое состояние с ограниченным polling; не добавляй произвольные `sleep`.
- Fake-сервисы должны иметь reset endpoints и отдавать записанные запросы или другое наблюдаемое состояние, необходимое для assertions.
- Проверяй наблюдаемое поведение и сохранённое состояние, а не последовательность внутренних вызовов, если она не является частью контракта.
- Для жеребьёвки проверяй инварианты на разных размерах и конфигурациях ограничений: полноту, уникальность, отсутствие самоназначений и запрещённых пар, а также корректный отказ для неразрешимых условий.

### Assertions и организация cases

- Для содержательных проверок используй `pyhamcrest`: `assert_that` и подходящие matchers (`equal_to`, `contains_string`, `has_entries`, `empty`, `none`, `same_instance` и другие).
- Не используй Hamcrest механически. Для одной очевидной проверки примитивного значения лаконичный `assert actual == expected` предпочтительнее громоздкого matcher-выражения.
- Если несколько тестов выражают одно правило и отличаются только входными данными и ожидаемым результатом, объединяй их через `pytest.mark.parametrize`.
- Не объединяй параметризацией сценарии с принципиально разным setup, потоком действий или смыслом ошибки.
- Имена тестов должны описывать поведение и ожидаемый результат. Для async-тестов полагайся на настроенный `asyncio_mode = auto`.
- Для исправления ошибки добавляй регрессионный тест, который падает без исправления.

## Стиль и инструменты

- Разделяй разные по смыслу блоки внутри функций пустыми строками для читаемости: подготовку данных, отдельные этапы операций, проверки и возврат результата.

Ruff настроен на длину строки 120 и правила `E`, `F`, `B`, `I`, `UP`, `SIM`. Pre-commit также запускает Ruff formatter и базовые проверки файлов.

Установка окружения, эквивалентная CI:

```bash
uv sync --locked --all-groups
```

Начинай проверку с самого узкого затронутого теста, затем запускай соответствующий набор. Перед завершением изменения кода по возможности выполни:

```bash
uv run ruff check .
uv run ruff format --check .
uv run mypy .
uv run pytest tests/units -q
uv run pytest tests/functional -q
```

Для документации, шаблонов и agent-инструкций запускай только относящиеся к изменению проверки файлов. Не запускай полные тестовые наборы, если код приложения не менялся и его уже проверенное поведение не затронуто.

Функциональные тесты должны самостоятельно поднимать PostgreSQL и Redis через Docker Compose на свободных локальных портах. Не полагайся на сервисы, заранее запущенные разработчиком.

Если полный релевантный набор запустить нельзя, выполни максимально близкую доступную проверку и явно укажи, что именно не запускалось и почему. Не утверждай, что проверка прошла, если команда не выполнялась успешно.
